## 1. Overview

When the Spec Management Software's AI generates suggestions during specification writing, those suggestions MUST be persisted to the filesystem for future reference by both humans and AI sessions.

---

## 2. Storage Location

```
{project-root}/
├── .lovable/

│               ├── YYYYMMDD-HHMMSS-S001.md
│               ├── YYYYMMDD-HHMMSS-S002.md
│               └── ...
```

---

## 3. File Naming Convention

### 3.1 Format

```
YYYYMMDD-HHMMSS-S{NNN}.md
```

**Examples:**
- `20260204-143022-S001.md`
- `20260204-143022-S002.md`
- `20260204-150000-S001.md` (new session, counter resets per session)

### 3.2 Session-Scoped Counter

The `S{NNN}` portion resets per AI session. For cross-session uniqueness, the timestamp provides disambiguation.

## 5. Tracker Integration

### 5.1 Auto-Update Tracker

When AI generates suggestions, the tracker is updated:

```markdown
## 📋 Pending Suggestions

| ID | Title | Type | Priority | Generated |
|----|-------|------|----------|-----------|
| S001 | Add validation rules to schema | Actionable | High | 2026-02-04 |
| S002 | Consider caching strategy | Informational | Medium | 2026-02-04 |
```

### 5.2 Completion Flow

1. User/AI works on suggestion
2. Status updated to `In Progress`
3. Work completed → Status = `Done`
4. File moved to `completed/` with `C-XXX` prefix

---

## 6. AI Behavior Rules

### 6.1 When to Generate Suggestions

| Trigger | Example |
|---------|---------|
| Spec creation complete | "Consider adding error codes for edge cases" |
| Gap detected | "This spec lacks database schema definitions" |
| Improvement opportunity | "The API could benefit from pagination" |
| Follow-up work | "Unit tests needed for this specification" |

### 6.2 Suggestion Quality Rules

- **Actionable**: Must be specific enough to execute
- **Non-redundant**: Check existing suggestions before creating
- **Scoped**: One suggestion = one task
- **Prioritized**: High = blocking, Medium = important, Low = nice-to-have

## 7. API for AI Sessions

### 7.1 Create Suggestion

```go
type CreateSuggestionRequest struct {
    Title       string
    Description string
    Type        string  // Actionable, Informational
    Priority    string  // Low, Medium, High
    SourceModule string
    RelatedSpec string `json:",omitempty"`
}

type CreateSuggestionResponse struct {
    SuggestionId string // S001
    FilePath     string // Relative path to file
}
```

### 7.2 List Suggestions

```go
type ListSuggestionsRequest struct {
    Status   string `json:",omitempty"` // Open, InProgress, Done
    Type     string `json:",omitempty"`
    Priority string `json:",omitempty"`
    Limit    int    `json:",omitempty"`
}
```

## Description

The Split DB architecture specification lacks a formal migration versioning system. As schemas evolve, there needs to be a standardized way to:

1. Track schema versions per database file
2. Apply forward migrations automatically
3. Support rollback for failed migrations
4. Validate schema consistency across distributed DBs

This is critical for production deployments where multiple CLI versions may interact with the same data files.
